**Correctness:** a few lines below this (the per-row "Rollout" button, `onClick={() => setVersion(r.version)}`), the click handler pre-fills the rollout version field with the **raw Object Store key** rather than the base version.

For a Linux release row, `r.version` is e.g. `0.45.4-linux-x86_64`. If the user then submits the rollout form, `POST /api/agents/rollout` writes `scope.target_version = "0.45.4-linux-x86_64"` verbatim — the backend doesn't strip the suffix either (`agent_releases.rs::rollout` stores `body.version` as-is).

That breaks the invariant documented just above in this same file ("A scope's `target_version` always names the BASE version… never `0.46.0-linux-x86_64`", mirrored in `kanade_shared::bin_platform::base_version_of_key`'s doc comment) and relied on by `self_update.rs::release_key_for_this_agent`, which appends its *own* arch suffix to whatever `target_version` is. A Windows agent (or a Linux agent of the other arch) resolving against a `target_version` that already carries `-linux-x86_64` would fetch a key that either 404s or — worse — resolves to a real object holding a binary built for a different platform, since the suffixed key does exist in the store.

The version-picker `<Select>` above (line ~248) correctly dedupes via `releaseBaseVersion(r.version)`; the per-row button should use the same helper: `onClick={() => setVersion(releaseBaseVersion(r.version))}`.
